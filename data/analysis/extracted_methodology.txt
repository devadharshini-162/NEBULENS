NEBULENS — Research-Backed Methodology & Implementation Plan

Nov 14, 2026 · @Deva Dharshini

1. Project summary and locked decisions

NEBULENS compares MODIS and VIIRS active-fire detections over Tamil Nadu on a common equal-area grid, day by day, and estimates how much of an apparent change in fire activity could come from the sensors instead of from the fires themselves.

Scientific boundary. NEBULENS produces comparable estimates; it does not claim that MODIS and VIIRS measure the same thing. Original observations are preserved untouched, sensor effects are modelled explicitly, and every adjustment must pass the validation tests in section 4 before the app shows it as "harmonised".

Research questions

How do MODIS and VIIRS hotspot counts and FRP differ over Tamil Nadu, by season, day versus night, scan angle and land cover?

Can a validated calibration make the two records comparable across 2000 to the latest standard-quality date?

How much of an apparent change in fire activity is associated with observation conditions rather than fire?

Does the calibration hold on years and places it was not trained on?

2. System architecture and data model

NEBULENS keeps what the satellites observed separate from what the model derives, so every derived number can be traced back to its source records.

architecture · 4 layers, 2 views

Rows run top to bottom as the four layers: acquisition and storage, harmonisation, analysis, web application. The API serves the observed view from the observations and daily grid, and the harmonised view from the harmonised table and analysis outputs.

Two views of the same data. The observed view shows what MODIS and VIIRS each detected, independently. The harmonised view shows derived, calibrated, comparable estimates. The app lets the user switch between them, and every harmonised row states whether it is an observed VIIRS value or a prediction made from MODIS.

Access. The FIRMS area API returns CSV for a bounding box: /api/area/csv/{MAP_KEY}/{SOURCE}/{west,south,east,north}/{DAY_RANGE}/{DATE}. The MAP_KEY is free, the limit is 5,000 transactions per 10 minutes, and /api/data_availability/ reports which dates each source covers. Use 5 days or fewer per request. Covering 2000 to the cutoff takes roughly 4,000 requests across all sources, well inside the limit. The archive download tool is the cross-check route.

Tamil Nadu extent. Request roughly west 76.2, south 8.0, east 80.4, north 13.6, a little wider than the state, then clip to the official boundary polygon. Treat these bounds as approximate until the polygon is loaded in M0.

Data pitfalls and how the plan handles them

Pitfall

Handling

NRT and standard data mixed

Standard replaces NRT as it becomes available (NASA pages say about 2 months in one place and about 5 months in another). Read the cutoff from data_availability, keep the version field, never mix in one series.

Archive file naming

A NASA Earthdata Forum user reported S-NPP downloads after September 2022 landing in a file named nrt rather than archive. Reconcile row counts against the API for sample months (task M1.6).

Confidence scales differ

MODIS confidence is numeric and VIIRS is low, nominal or high; FIRMS states they are not the same scale. Keep the raw value, derive a class per sensor, filter each sensor independently.

Static and non-vegetation heat sources

The type attribute in standard data separates vegetation fire, volcano, static land source and offshore. Keep rows flagged; exclude non-vegetation types from the main series. Tamil Nadu has industrial heat sources and a long coastline.

Day boundary

Night overpasses fall either side of midnight UTC. The analysis day is the IST calendar day; UTC time is kept.

Overpass times drift

Nominal local times (VIIRS about 13:30 and 01:30) are not guaranteed over 26 years. Build per-year acquisition-time histograms (task M2.9).

Terra has no coincident VIIRS pass

If Terra's nominal morning overpass holds, no VIIRS pass is near-simultaneous with it, so Terra can only be compared on the daily grid. This supports the daily-grid decision.

Monsoon cloud

The northeast monsoon brings heavy cloud over Tamil Nadu, cutting valid observations. Coverage proxies and exposure terms are part of calibration (M3, M4).

The exact end date of standard data is not fixed here; the pipeline reads it from the availability endpoint on the day it runs.

4. Methodology

The method runs in five steps: clean and flag, aggregate daily on the grid, calibrate, validate, then analyse; a model reaches the app only if it passes validation.

4.1 Cleaning and flagging

Clip to the Tamil Nadu polygon. Offshore rows are marked, not deleted.

Flag non-vegetation types and persistent hotspots (the same location detected on many distinct days each year; the threshold is tuned in M2).

Platforms that overlap in time, such as S-NPP and NOAA-20, can see the same fire on the same day. Group those into a duplicate_group so repeat sightings are not counted as separate fires. The original rows stay.

Never remove a MODIS detection because VIIRS also saw something nearby. Matching identifies candidate correspondences; it does not merge or delete.

4.2 Daily grid aggregation

Every cell-day gets the same set of measures, for each sensor family.

Zero rows are kept for every cell-day so the count models see the zeros. That is about 1,300 cells times about 9,500 days, roughly 12 million rows for the full record, which Parquet handles comfortably.

Overpass-level diagnostic (not the main pipeline). For Aqua and VIIRS, which both pass at about 13:30 local time, build a pair-link table of candidate near-simultaneous detections. Starting thresholds are a centroid distance of about 1 km and a time gap of 15 minutes, tuned in M3 with sensitivity at 0.5 and 2 km and 10 and 30 minutes. This follows the near-simultaneous matching used by Fu et al. (2020). The table feeds validation and the FRP model only; it never changes the daily counts.

4.3 Calibration

Calibration predicts the VIIRS-equivalent value for a cell-day from the MODIS observation, with observation opportunity as an exposure term. A regression on raw counts alone is not trusted.

\log \mathbb{E}[V_{c,d}] = \log(e_{c,d}) + \beta_0 + \beta_1 \log(1 + M_{c,d}) + \gamma_{\text{season}(d)} + \delta_{\text{landcover}(c)} + \theta^{\top} z_{c,d}

Here V is the VIIRS count in cell c on day d, M is the MODIS count, e is the exposure (observation opportunity), and z holds coverage and geometry covariates such as day or night share, scan-angle mix and platform. If zeros make daily fits unstable, the fallback is weekly cell totals; M3 checks the zero fraction and M4 checks convergence and calibration plots before that choice is made.

Optional

A more complex model replaces a simpler one only if it improves held-out error and calibration by a margin fixed before the test data are opened, and does not worsen the sensor-transition test.

FRP is modelled separately from counts, in two parts. First, per-fire FRP in Aqua and VIIRS linked pairs, with scan angle as a covariate: Li et al. (2018) found MODIS mean FRP can rise by up to 300% at the scan edge relative to nadir, while VIIRS stays fairly stable across the swath. Second, total FRP per cell-day using a log-scale robust or gamma model with the same exposure terms. The split matters because Fu et al. (2020) found MODIS FRP higher for fires both sensors saw, yet monthly total FRP higher for VIIRS because MODIS misses more fires. Those two effects must not be blended into one number.

Exposure and coverage, in three tiers. FIRMS files list only detections, so an empty cell-day says nothing about whether a sensor looked there. Coverage therefore needs help.

Tier 1, from the detection records: day and night presence, overpass clusters, scan-angle mix.

Tier 2, auxiliary data: a daily cloud-cover covariate (source chosen in M3) and orbit-based overpass counts.

Tier 3, advanced: a detection-probability operator after Sofiev and Kouznetsov (2026), who estimate a MODIS C6.1 detection limit of about 3.7 MW for a nadir clear-sky night retrieval, up to 40 MW for a daytime side view, and about 0.5 MW for VIIRS at night. This is a research direction, not a promise to reproduce the paper in full; their code is archived on Zenodo.

4.4 Validation

Validation is mandatory, not a late extra. The harmonisation has to show it improves comparability on data it was not fitted on. Splits are by time and by spatial block, never random, because neighbouring cells and consecutive days would otherwise leak into the test set and make results look better than they are.

All numeric thresholds are written into the config in M4, before the test data are opened, so they cannot be tuned to the result. A failed test is reported, and the affected output stays labelled "not validated" in the app.

4.5 Sensor impact and fire-activity attribution

This module decides how an apparent change should be described. It reports an evidence assessment, never a single claimed cause, because hotspot records alone cannot prove why a count changed.

Evidence pattern

Possible reading

Count rises, FRP stable, coverage rises

Possible observation effect

Count and FRP both rise

Consistent with increased fire activity

Detections and burned area both rise

Stronger supporting evidence

Count rises while cloud or coverage shifts a lot

Attribution uncertain

Indicators per region and period: change in n_unique against the seasonal baseline, change in FRP (median and total), change in coverage and exposure, change in cloud cover, repeat-detection persistence, spatial spread (number of active cells) and burned-area change. "Changed" is judged against the history of the same region and season using the robust score in 4.6, not against fixed cut-offs.

Output classes: likely sensor-related change, consistent with increased fire activity, mixed effects, insufficient evidence. Each result ships with its evidence table so the user can see why. An illustrative sentence: "Fire detections rose 35% against the historical baseline, but observation coverage also changed, so the rise cannot be attributed entirely to real fire growth." The 35% is an example, not a result.

4.6 Historical comparison and anomaly detection

Start with statistics, not deep learning.

Baseline: the same calendar window across years (March 2026 against earlier Marches, not against February).

Like with like: MODIS-only history is compared with MODIS, harmonised with harmonised. 2000 to 2011 is MODIS only; from 2012 both sensors exist.

Robust score from the rolling median and the median absolute deviation (MAD):

z = 0.6745 \, \frac{x - \operatorname{median}(x_{\text{baseline}})}{\operatorname{MAD}(x_{\text{baseline}})}

A conventional flag threshold of 3.5 is the starting point and is reviewed against Tamil Nadu's own distribution.

Sparse counts break this: in many cells the MAD is zero. Fallback: score at district or state level, or use a negative binomial exceedance quantile instead of z.

Seasonal decomposition is used only at monthly regional level, where enough years exist. Machine-learning anomaly detection is a later extension.

Each comparison reports average monthly detections, total FRP, active-fire days, spatial distribution, anomaly score and, where available, burned area.

4.7 Burned area as independent evidence

A hotspot is a thermal detection at the moment a satellite looks; it does not give burned area in square kilometres. MCD64A1 C6.1 maps monthly burned area at 500 m using surface reflectance and active-fire observations, with burn date and quality layers. NEBULENS aggregates it to the grid and district level and uses it only as supporting evidence in 4.5. It is monthly and may miss very small burns, so it never overrides the daily hotspot record.

5. Web application design

The app is an explorer where a user can see what each sensor detected, see the harmonised view beside it, and ask why a change was flagged.

Stack. React with TypeScript and Vite; MapLibre GL JS for maps; a charting library such as ECharts or Recharts; TanStack Query for data fetching. Backend: FastAPI with Pydantic models, DuckDB reading the Parquet tables.

Rules the interface follows

Every series is labelled with its sensor and provenance. Pre-2012 harmonised values are drawn differently and marked as predicted from MODIS.

6. Implementation plan

The work is ten milestones, M0 to M9, about 69 focused days in total as a rough estimate. A focused day means roughly three to four hours; rescale to the time you actually have. Each task is sized for a day or less, and each milestone ends with a "done when" check, so progress is measured against the agreed method instead of drifting. Three gates stop the project from moving on too early: Gate A after M3, Gate B after M5, Gate C after M8.

roadmap · 7 phases, 3 gates

The gates are decision points: A decides whether calibration is worth doing, B decides which harmonised outputs go live, and C decides whether the app is ready to release. The highlighted phase is the project's core contribution.

7. Research bibliography, risks and open items

Seven papers shape the method, listed in reading order. Links were checked on 14 November 2026. Findings below come from abstracts and publisher summary pages; read the full papers before quoting numbers in a report.

Research papers

#

Reference

Why it matters here

Link

1

Li, Zhang, Kondragunta and Csiszar (2018). Comparison of Fire Radiative Power Estimates From VIIRS and MODIS Observations. Journal of Geophysical Research: Atmospheres 123(9), 4545-4563

VIIRS FRP is fairly stable across the swath; MODIS mean FRP can be up to 300% higher at the scan edge; the sensors differ about 20% on 1 degree grids in fire-prone regions and the relationship changes with spatial scale. Supports scan-angle terms and separate FRP and count treatment

DOI, NOAA repository

2

Schroeder, Oliva, Giglio and Csiszar (2014). The New VIIRS 375 m active fire detection data product: Algorithm description and initial assessment. Remote Sensing of Environment 143, 85-96

Describes the 375 m algorithm; reports 3 times (day) and 25 times (night) more fire pixels than the VIIRS 750 m baseline, and commission error under 1.2% for nominal-confidence pixels. Raw counts across products are not equivalent

DOI

3

Fu, Li, Wang, Bergeron, Valeria, Chavardes, Wang and Hu (2020). Fire Detection and Fire Radiative Power in Forests and Low-Biomass Lands in Northeast Asia: MODIS versus VIIRS Fire Products. Remote Sensing 12(18), 2870

MODIS missed 65% (forest) and 83% (low-biomass) of VIIRS fire pixels, VIIRS missed 35% and 53% of MODIS pixels; monthly total FRP higher for VIIRS but FRP of jointly detected fires higher for MODIS. Basis for land-cover-aware calibration and near-simultaneous matching

Paper

4

Sofiev and Kouznetsov (2026). Observation operator and detection limits for MODIS and VIIRS Fire Radiative Power products. Geoscientific Model Development 19, 10123

Detection limit as a function of pixel area; about 3.7 MW (MODIS, nadir, clear-sky night) to 40 MW (daytime side view), about 0.5 MW for VIIRS at night; global detection probability of powerful fires 78% for MODIS and 88% for VIIRS. Basis for the advanced Tier 3 operator

DOI, code on Zenodo

5

Vadrevu and Lasko (2018). Intercomparison of MODIS Aqua and VIIRS I-Band Fires and Emissions in an Agricultural Landscape. Remote Sensing 10(7), 978

An Indian precedent (Punjab): VIIRS detected several times more fires than MODIS, monthly FRP was strongly correlated (r squared 0.98), and a MODIS plus VIIRS model was used to extend the record. Close to what NEBULENS attempts, for a different region

DOI, open text

6

Sharma, Wang and Lennartson (2017). Intercomparison of MODIS and VIIRS Fire Products in Khanty-Mansiysk Russia: Implications for Characterizing Gas Flaring from Space. Atmosphere 8(6), 95

Different products and spectral bands respond differently to small, hot sources such as flares. Supports sensor metadata preservation and careful handling of static industrial heat sources

DOI

7

Giglio, Boschetti, Roy, Humber and Justice (2018). The Collection 6 MODIS burned area mapping algorithm and product. Remote Sensing of Environment 217, 72-85

Method behind MCD64A1: 500 m burned area from surface reflectance and active fires; better detection of small burns than the previous collection

DOI, open text

A correction to earlier notes: the 2026 paper is by Sofiev and Kouznetsov, not "Kouznetsov et al.".

Risks

Risk

Mitigation

Fire counts in Tamil Nadu are sparse, so models and robust scores can be unstable (MAD of zero)

Weekly or district aggregation; negative binomial exceedance fallback (M3.7, 4.6)

Pre-2012 harmonised values are predictions from MODIS, not observations

Labelled predicted_from_modis, wider intervals, temporal holdout test (M5)

Terra and Aqua overpass times drift, or MODIS data end

Per-year acquisition-time histograms, platform covariate, plan for a VIIRS-only future (M2.9)

Coverage and cloud cannot be seen in detection files

Tiered coverage proxies; outputs that rely on weak proxies are labelled

Findings from other regions may not transfer

Fit and validate on Tamil Nadu only; report per land-cover class

NRT and standard data mixed

Version field kept; cutoff read from the availability endpoint (M1.1, M1.7)

Scope creep

Gates A to C; no interface work before Gate B
